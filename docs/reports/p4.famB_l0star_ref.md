## What was run

- **Model.** ExactColoc in simulator-prior mode, using the exact `src/sim/l0star.py` prior
  (`famB.priors.sim_prior_from_l0star`: type table plus per-trait 8-component scale mixture, with the 2 all-zero components dropped, K = 6).
  - The runner asserts that this prior equals the one recorded in `l0star_v2.stats.json` (weights, sds, type prior, η, trait kinds).
  - A test covers this, with a negative control that perturbs one weight.
- **Inputs.** η = η_floor = 0, because the set stores R̃ = 0.999R + 0.001I, the matrix the data were generated with. ρ = the true ρ (`rho_hat` attribute).
  - p = 20 ≤ M, so there is no screen and no collapse. The enumeration covers all configurations with ≤ 2 causal variants per trait (48,455,521 terms per locus).
- **Outputs.** Hypothesis PPs are exact sums. The 5 oracle-class posteriors (S, U, D, W, G) are Monte Carlo estimates.
  - **4 independent replicates × 65,536 stratified draws = 262,144 draws per locus.**
  - Replicate r of locus L draws from `derive(20261029, "famB_mc", "l0star_ref_rep{r}", L)`, so draws are keyed per locus (see "Batch invariance" below).
- **Command.** `python -m famB.l0star_ref --set data/processed/sets/l0star_v2.h5 --out results/famB/l0star_ref --n-mc 65536 --reps 4 --compile`
  - Wall time: 4 × ≈ 345 s on the RTX 4090; peak VRAM 2.6 GB.

**Output** `posteriors.parquet` has one row per locus (2,000 rows) with these columns:
- `P_S, P_U, P_D, P_W, P_G`: the replicate mean. They sum to 1, and `P_W` is the strict W class.
- `se_*`: replicate SD / √4.
- `PP_H0…PP_H34`: exact, and identical across replicates (max |Δ| = 0).
- `rho_used`, `n_mc` (262,144), `status`.

`run.json` holds the configuration and prior. `calibration.json` holds the evaluation below.

## Calibration against the l0star_v2 oracle labels

The set is class-stratified: 500 each of S, D, W and G, with U never stored. The two readings follow P3-4:
- **Natural.** Loci are weighted to the natural class shares given c ≠ U, using `stats.json` (S 0.0524, D 0.0627, W 0.7927, G 0.0921). B's posterior is conditioned on c ≠ U.
- **Balanced.** Loci are unweighted. B's posterior is re-weighted to the 0.25 class prior (`priors.reweight_classes`).

For an exact posterior, E[cross-entropy] = E[posterior entropy] (the Bayes-optimal log loss). SEs come from a cluster bootstrap over 111 LD blocks with 2,000 replicates (`eval.metrics.cluster_bootstrap`). Command: `python scripts/famB_eval/l0star_calibration.py` (same job).

| | natural | balanced |
|---|---|---|
| cross-entropy of B (nats) | 0.1726 ± 0.0072 | 0.3299 ± 0.0135 |
| E[entropy of B's posterior] | 0.1824 ± 0.0074 | 0.3482 ± 0.0144 |
| CE − entropy (0 if Bayes-optimal) | **−0.0098 ± 0.0090** (95% CI −0.027, 0.009) | **−0.018 ± 0.013** (−0.042, 0.007) |
| prior-only cross-entropy (class shares) | 0.7321 | — |
| ECE, 10 bins (S / D / W / G) | 0.003 / 0.003 / 0.008 / 0.011 | 0.011 / 0.011 / 0.010 / 0.015 |
| mean predicted vs target share (S / D / W / G) | .050/.052, .061/.063, .794/.793, .095/.092 | .243, .247, .249, .261 vs .25 |

- **Log loss.** CE − entropy is consistent with 0 in both readings. B uses 76% less log loss than the class prior alone.
- **Reliability.** 79 bins with n ≥ 10 across classes and both readings have a maximum |z| of 2.88. That is the size expected for the largest of 79 approximately normal deviates, and no class shows a monotone trend.
  - The largest deviations are W [0.2, 0.3) (natural, z = −2.4) and G [0.8, 0.9) (n = 22, z = −2.3).
  - The z values use the Kish effective n and ignore block clustering, so they slightly overstate significance.
- **Per class.** The mean posterior on the true class (natural, given c ≠ U) is S 0.81, D 0.79, W 0.96 and G 0.48. G is intrinsically hard, because the oracle's grey thresholds sit inside the posterior effect mass.

**Conclusion.** On l0star_v2@2, B's simulator-prior posterior is calibrated and achieves the Bayes-optimal log loss within bootstrap error. It is fit for use as the Family C C1 reference.

C1 should compute KL(B ‖ C) over the 5 classes. If C excludes U, KL should be computed over S, D, W, G after conditioning both on c ≠ U, with the P3-4 natural weights. The MC error of B (SE ≤ 0.0024 per class) adds a small upward bias to an estimated KL, of about Σ_c SE_c²/(2P_c). On average this is ≪ 0.02 except for loci where a class has P ≈ 0; flooring at 1/n_mc handles those.

## Batch invariance (verifier finding, fixed before this run)

- **Original defect.** Before commit `0e3d4ac`, one torch generator was shared by every locus in a batch, so a locus's MC draws depended on batch composition and order. The seed was also not taken from `common.seeds`.
- **Fix.** Every locus now has its own generator, seeded with `derive(seed, "famB_mc", seed_key, locus_id)`, and the seed must be in `SEEDS`.
  - Changed files: `src/famB/enum.py` (`rand_rows`), `events.py` and `method.py`.
- **Test.** `tests/famB/test_batch_invariance.py` covers both sampling paths. It evaluates 6 loci in four batch compositions (full, reversed, singletons, a subset of 3).
  - The MC outputs (s, P_S, P_D, P_W, E1, E2, P_U, P_G, P_W_strict) must be bitwise identical.
  - Exact PPs and PIPs must agree to ≤ 1e-12. GPU reduction order differs by about 1e-16.
  - A different `seed_key` must change the draws, and a seed outside `SEEDS` must raise.
  - Results on GPU (job `famB_tests_p4`, commit `0e3d4ac`): every MC field was bitwise identical across batch compositions. Two checks failed, both test-side issues fixed in `4a2d676`:
    - the exact (non-MC) PIPs differed by 2e-16, so the tolerance on exact quantities is now 1e-12;
    - the word "truth" appeared in a docstring of `src/famB/l0star_ref.py`, which the static truth-isolation test rejects.
  - Full suite after the fix (job `famB_tests_p4_r3`, CPU, commit `cac6d4e`): `python -m pytest tests/famB -q` → **43 passed, 2 skipped**. The 2 skipped tests are the compile tests, which run on GPU only; they passed in `famB_tests_p4`.
  - The GPU re-run (`famB_tests_p4_r2`) was cancelled because the GPU was full.
- **Earlier run discarded.** An earlier run with the shared generator (job `famB_l0star_ref_v1`) was cancelled before writing output. Nothing from the old code was registered, so there is no stale @1.
