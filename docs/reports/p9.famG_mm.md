# p9.famG_mm — G-mm, a GPU port of mismatch-aware coloc-SuSiE (engineering note)

**Scope.** Owner: famG agent. Branch `p9-famG-mm`. Shipped and timed build: commit **bcc841f** (GPU, fp64 everywhere, Triton kernels; DECISIONS P4-6).
- Code: `src/famG/susie_mm.py` (engine), `src/famG/mm_kernels.py` (Triton), `src/famG/method_mm.py` (Method `GPUColocSusieMM`), `src/famG/ld.py`.
- Validation and timing scripts: `src/famG/validation/{mm_loci, run_susie016_mm.R, run_wrapper_mm, compare_mm, run_traj_mm.R, traj_mm, sens_mm, bench_mm, timing_mm}.py|.R`, plus `timing_job.sh`.
- Tests: `tests/famG/test_susie_mm.py`, 6 passed on bcc841f (job famG_mm_perf_v7).
- Results: `results/famG_mm/` (not committed).

## Verdict
- **The correctness rung FAILED as pre-registered.** Identity holds on 199/200 fits. One chaotic, non-converged fit (`valid_grid_v1__L4_P1_r_p=0.0__W__0007201`, trait 1) falls outside the amended P4-3a bound. G-mm is therefore a report-only engineering note and not a candidate (P4-6).
- **Throughput (§7.7, exclusive slot, 2,000-locus M4 slice):** G-mm processes **31,838 loci/h** (median of 3 runs) on 1 GPU. That is **4.77× coloc_susie_mm** (6,670 loci/h, median of 3, 40 memory-limited workers on 64 cores). This is **short of the DESIGN_P2 5× bar** and of the C2 10× stretch. Against coloc-SuSiE 0.14.2 the ratio is **4.18×** (n = 1 repeat), short of DESIGN C2's 10×.
- **Diagnosis of the speed gap:** in the timed configuration about 130 s of each about 220 s G-mm run is the single harness worker reading 2,000 loci from HDF5; the GPU fit itself is about 90 s (§3).
- **The G-mm M4 run was dropped** by PI decision P4-7, because G-mm is not a candidate.

## 1. What was ported
The target is exactly the coloc_susie_mm wrapper call: `src/baselines/r/worker.R:fit_susie` gives `susie_rss(z, R, n, L = 10, R_finite = n_ref, R_mismatch = "eb_mix")` with susieR 0.16.6 (env/src/susieR, 97feba5), then `coloc.bf_bf` on the credible-set rows of `lbf_variable` (p1 = p2 = 1e-4, p12 = 5e-6), then the DESIGN §4.3 adapter, with a coloc.abf fallback (W = 0.15).

**Ported line by line.** Every R function is named in the docstring of `susie_mm.py`.
- **Defaults.** PVE-adjusted z; XtX = (n−1)R with susieR's standardisation; σ² fixed at 1; V initialised to 0.2; prior weights `log(1/p + √ε)`; `max_iter = 50` (the RSS default when the wrapper passes none); `tol = 1e-4`; `check_prior = TRUE`.
- **Initialisation** (`initialize_R_mismatch`). One SER on effect 1, then λ from the fitted residual, scaled by the LD coherence α₁'(R∘R)α₁ over the variants with α ≥ 2/p. The effect-1 fit is kept as a warm start.
- **Per-effect inflation** (`compute_shat2_inflation`). infl_j = 1 + (1/B + w_j λ) s_j/σ², with s_j = (XtXr₋ₗ)_j²/(n−1) + max(b₋ₗ'XtXr₋ₗ, 0). The eb_mix gate w_j (`compute_mixture_gate`) applies only when λ > 0 and is computed as in R:
  - prior log-odds ½(max z² − z_ref²), with z_ref = qnorm(2.5e-8, upper);
  - `plogis` as 1/(1+exp(−x)), including R's overflow to exactly 0;
  - V_sig by `optimize` (tol 1e-6) on the 2-component mixture, with R's bounds, its type-7 0.99 quantile and its degenerate branches.
- **SER.** Closed-form `gaussian_ser_lbf`. Prior variance by `optim(method = "Brent")` on log V ∈ [−30, 15], then the keep-old rule and the null check.
- **λ after every sweep** (`estimate_lambda_bias`, MLE). Upper-bound expansion loop, `optimize` with tol 1e-8, the nll(0) check, and the 0.1·SE₀ floor.
- **Convergence** (`check_alpha_pip_cycle_convergence`). Iteration 1 never converges. After that, max(|Δα|, |ΔPIP|) < tol at lag 1, or at lags 2–5 (a short cycle, with α averaged over the cycle). Then the λ guard: if |Δλ| > tol the fit is not converged, but the averaged α is kept.
- **Failure.** The `validate_prior` stop when any V > 100·max|z|² is reproduced as status `failed`.
- **Output.** `trim_null_effects`; credible sets as `susie_get_cs`, with exact purity (cov2cor of XtX) over all members; PIP over effects with V > 1e-9.

**Skipped, with the reason they cannot change any returned quantity:**
- eigen(R), Q_art, artifact/reliability flags, BF attenuation and the one-SER `ser_model` are diagnostics only.
- The ELBO: with forced PIP convergence it matters only through `get_objective`'s `is.infinite()` stop. On the ss path `compute_augmented_eloglik_ss` reads `data$predictor_weights`, which is NULL there, so the data term is the constant −p/2·log 2π and the ELBO is always finite.
- These two skips are what make the R baseline spend time in eigen(R) and in an O(L·p²) ELBO every iteration.

**Engine.**
- Loci are bucketed by p (ratio ≤ 1.5); both traits of a locus share one LD.
- LD is stored as dense R, or as the factor X when n_ref < p.
- All three 1-D optimisations are exact ports of R's `Brent_fmin`, fused into one Triton program per fit row. Inactive rows are skipped inside the kernels.
- The fp64 LD products use memory-bound Triton batched GEMVs.
- Several buckets run concurrently on CUDA streams (3 picked in the slot).
- The LD coherence uses only the α ≥ 2/p block, as susieR's `XtX[keep, keep]` does.

## 3. Throughput (DESIGN §7.7)
Job famG_mm_timing_v1 (commit bcc841f) ran on the whole machine (64 cores, the GPU, nothing else scheduled) at priority 12, 16:17–18:12.

**Protocol.**
- **Harness.** Every repeat is a harness run (`eval.harness.run_method`, `timing=True`, exclusive timing + machine lock) on the fixed 2,000-locus M4 slice (artifact `famG_mm_slice2000@1`, a seeded draw from m4_subsample@1 main).
- **LD I/O.** Each locus is read from `valid_grid_v1.h5` by the harness worker, so LD I/O is included. All repeats ran after one untimed page-cache pre-warm (22.4 GB read in 11.6 s with 16 readers), so every method saw the same warm cache.
- **Whole-machine throughput** = 2,000 / harness wall time.
- **G-mm.** 1 harness worker with one 2,000-locus batch, fp64, 9 GB bucket budget (torch peak 16.6 GB), 3 concurrent CUDA streams. The stream count was picked inside the slot by a 2-configuration bench on 512 strided slice loci: fit-only 14.5 loci/s with 1 stream, 22.2 with 3.
- **CPU baselines.** Memory-limited per §7.7: at most 2 GB per core gives 128 GB. The measured worst-case worker peak is R 2.7 GB + python 0.5 GB (identity run), so floor(128/3.2) = **40 workers**. Single-threaded BLAS, longest-p-first order, wrapper default timeouts (900 s / 600 s).

**Repeats.**
- The plan was 3 × G-mm, 3 × coloc_susie_mm, then coloc-SuSiE 0.14.2.
- The 115-min orch timeout ended the job during the 2nd 0.14.2 repeat. **That partial repeat is discarded.**
- The result is the PI's pre-declared fallback set: 3 × G-mm, 3 × coloc_susie_mm, 1 × 0.14.2.

| Method | Workers | Wall s per repeat (2,000 loci) | Loci/h (median) | Status counts |
|---|---|---|---|---|
| **G-mm (GPU, fp64)** | 1 GPU + 1 harness worker | 234.0, 212.7, 226.1 | **31,838** | 0 failed, 248 non-converged (identical in all 3) |
| coloc_susie_mm (susieR 0.16.6) | 40 CPU | 1088.8, 1045.4, 1079.5 | **6,670** | 0 failed, 249 non-converged |
| coloc-SuSiE (susieR 0.14.2) | 40 CPU | 944.4 (n = 1) | **7,624** | 5 failed, 452 non-converged |

**Ratios (whole machine, the pre-registered unit).**
- **G-mm vs coloc_susie_mm: 4.77×** (medians; 4.78× with means; 4.47–5.12× over all repeat pairs). **Short of the 5× bar.**
- **G-mm vs coloc-SuSiE 0.14.2: 4.18× (n = 1).** Short of DESIGN C2's 10×.
- Secondary, not pre-registered: if coloc_susie_mm scaled ideally to 64 workers (ignoring the §7.7 memory limit), it would reach 10,671 loci/h, and the ratio would be 3.0×.
- Per worker, the comparison is one GPU against one core.
  - coloc_susie_mm averages 20.9 worker-s per locus: median 14.5 s, p95 61.2 s.
  - Its median (p95) per-locus runtime in s by mismatch level: L0 13.1 (55), L1 13.4 (59), L2 13.7 (60), L3 12.3 (62), L4 18.8 (76), L6 11.9 (49).
  - coloc-SuSiE 0.14.2: all 7.5 s (75); L0 3.5, L1 4.5, L2 11.4, L3 15.7, L4 30.6, L6 10.8.
  - G-mm takes 0.113 s per locus, amortised over its batch. It has no per-locus timing, because loci are fitted together.
- **Scaling in p** (500/2k/5k/10k): not measured. The slice spans p ≈ 1,000–5,400, and there was no slot time for synthetic p = 500/10k loci.

**Diagnosis of the gap to 5×.**
- G-mm's GPU fit takes about 90 s per 2,000 loci (22.2 loci/s fit-only, measured in the slot).
- The remaining about 130 s of the about 220 s wall time is the single harness worker reading 2,000 loci from HDF5 serially before it fits: about 65–70 ms per locus even from page cache (measured 37 s per 512 loci in the bench).
- At fit speed alone, G-mm would process about 80,000 loci/h, about 12× coloc_susie_mm. That is an untimed extrapolation, not a measurement.

**Post-hoc engineering diagnostic, not a pre-registered measurement.** It is not the headline, and no bar is evaluated on it.
- After the timing job (job famG_mm_timing_diag_v1, same machine state), one run used 4 harness workers × 250 loci (streams 3, 2.5 GB each) to overlap reading and fitting.
- It took **548.8 s (13,118 loci/h)**, worse than 1 worker.
- Without MPS the 4 CUDA processes time-slice the GPU, and the smaller batches fragment the buckets.
- Overlapping I/O therefore has to be done inside one GPU process, with reader processes prefetching the next batch. That is not implemented.

## 4. Performance diagnostics (development, co-resident GPU; not §7.7 numbers)
These are fit-only loci/s on 512 strided slice loci (`bench_mm.py`), with the GPU shared with C/B jobs and a 4.5 GB per-process VRAM cap. They are diagnostic only.

| Commit | Change | Fit loci/s | Dominant GPU cost (torch profiler) |
|---|---|---|---|
| 14f0ecd | first GPU build, fp32 LD, 1.5 GB buckets | 2.35 | Brent kernel 78% (≈ 2.5 ms per launch at any row count: one program per fit row is per-SM-fp64-bound, so small buckets are latency-bound); per-SER host syncs |
| 9875f10 | fp64 LD, no host syncs, bigger buckets | 2.58 | fp64 LD products 41% (cuBLAS/cutlass fp64 tensor-op GEMM pads the 2-row operand to a full tile); fp64 X'X formation 17%; Brent 35% |
| d8f5815 | Triton fp64 batched GEMV; streams code | 3.86 | — |
| 03e4df6 | kernels skip inactive rows (bit-identical results) | 6.14 | — |
| 73e8678 | (re-profile) | 4.71 | Brent 48%; full-p LD-coherence Hadamard GEMM 23%; GEMV 14% |
| bcc841f | coherence on the α ≥ 2/p block only (shipped) | 6.06 | — |
| bcc841f, exclusive slot, 9 GB budget | streams 1 / streams 3 | **14.5 / 22.2** | — |

- **fp64 vs fp32:** on the first GPU build, fp32 LD and fp64 LD ran at the same speed (2.35 vs 2.58 loci/s). The cost is in the fp64 Brent objective evaluations, not in the LD products. A clean fp32 rerun on bcc841f printed no result line (job famG_mm_perf_v6, acked), and fp32 is not shipped, so it was not repeated.
- **Where the remaining time goes:**
  - fp64 transcendental work in the per-row Brent searches (RTX 4090: 1/64-rate fp64);
  - the launch latency of non-converged tails, which concurrent streams partly hide;
  - in the harness configuration, serial HDF5 reading (§3).

## 5. Reproduce

```
# P4-3 spread: MM_PERT=1e-14 MM_SEED=s Rscript ... run_susie016_mm.R $W $O/pert/s$s <nonconverged ids>, s = 1..10

    --gpairs $O/cmp_v7/pairs_float64_cuda.tsv --ids $O/nonconv_ids.txt --out $O/sens_v7
PLAN=gmm:3,mm:3,cs:1,cs:2 OUT=results/famG_mm/timing_v1 bash src/famG/validation/timing_job.sh             # §7.7 (exclusive)
```
