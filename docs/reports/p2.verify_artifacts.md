**Is fb426c4 a concern for the stored sets? No.** fb426c4 only adds a fallback `level = level or src.level` in `rho_hat_for`. The cell builder's `finalize` always passes the cell level explicitly (`rho_hat_for(ps, z1, z2, src, g, level)`), so fb426c4 is a no-op for set building. The regeneration confirms it: `rho_hat` and `rho_se` are bit-identical in every sampled locus, in both the locus attributes and the truth. No rho-hat recompute job is needed.

## 1. Deterministic regeneration (`scripts/p2_verify/regen_sample.py`)

**What determines a locus.** Each locus depends only on (window, cell, candidate index k). The calls are the same ones `sim.cells._visit` makes:
- `draw_candidate(ctx, cell, rng(seed, set, cell_id, "cand", k))`
- then `finalize(ctx, cand, rng(seed, set, cell_id, "fin", k), locus_id)`

The inputs come from the stored data:
- **k:** the truth column `cand_index`.
- **ctx:** the `split_windows("valid")` row matching the truth columns `window_chr`, `window_start`, `window_end` and `anchor`, constructed exactly as in `build_set`.
- **Determinism settings:** `CUBLAS_WORKSPACE_CONFIG=:4096:8`, `use_deterministic_algorithms`, TF32 off.

**Cell specs.**
- screen_v2: `sim.cells.screening_cells()`.
- valid_grid_v1: `sim.testset.main_grid_cells(cfg, "valid")`, giving P1 nested and P3 with both signs. The `main_grid` levels and pairing_overlap were copied from `configs/testset_v1.yaml` on branch p2-review-wip (2cc5e60), because that config is not in master.

**Seeds.** screen_v2 used seed 20261027 and valid_grid_v1 used 20261029. Both used K = 200 and M = 3 (stats json).

**Sample.** Seeded with `rng(seed, "p2.verify_artifacts", set, "sample")`.
- **screen_v2:** 72 loci, 3 per (cell, bucket) across 6 cells and 4 buckets:
  - In each bucket: the first accepted k, the last accepted k, and one random k.
  - k ranges over 0–62,118, so the sample spans the whole build, including both sides of the 18:26 commit.
  - Classes: S 18, D 36, W 18. There are 31 windows.
- **valid_grid_v1:** 102 loci, 3 per cell across all 34 cells:
  - Classes rotate over S/D/W/G/U: S 20, D 20, W 21, G 21, U 20.
  - Every level L0–L4 and L6, and every pairing and overlap, is covered.
  - k ranges over 120–19,877, in 59 windows.

**Compared fields (94).**
- Locus arrays: z1, z2, beta1/2, se1/2, n1/2, maf1/2, maf_ref (float64); variant_id; pos.
- LD: `R` or `X_ref` (float32, compared exactly in the stored dtype).
- L0 trait-2 LD `R2`/`X_ref2`, with `ld_type2`/`n_ref2`: 12 loci in screen_v2, 6 in valid_grid_v1.
- Locus attributes: ld_type, n_ref, rho_hat, rho_se, split, level, pairing, cell_id, window, block_ids, trait types. Any stored attribute that is not regenerated is flagged.
- All 63 truth columns, including oracle class, mu, r2, d, causal indices and effects, pve, rho_hat/rho_se/rho_mode/rho_n_used, p, flipped, seed_key, bucket and cand_index.

**Results** (`results/p2_verify_artifacts/regen_{screen_v2,valid_grid_v1}.json`):

| Set | Loci | Identical | Fields not identical | Max \|diff\| | Runtime | Peak GPU |
|---|---|---|---|---|---|---|
| screen_v2 | 72 | 72 | none | 0.0 | 17 s | 1.08 GB (torch), 0.65 GB (nvidia-smi) |
| valid_grid_v1 | 102 | 102 | none | 0.0 | 35 s | 2.32 GB (torch), 2.88 GB (nvidia-smi) |

The regenerated oracle class equals the stored class for every locus.

**Why the GPU.** The sets were built on the GPU (float32 cuBLAS), so bit-identity can only be tested on the same device. A CPU replay would differ at float32 rounding level, which is not a reproducibility failure. The jobs declared 7 GB of VRAM and stayed under 3 GB.

**The comparator was tested** with `scripts/p2_verify/compare_sets.py`, which shares the `_diff` logic:
- Self-compare of l0star_v1: identical.
- Copy with one z1 entry changed by 1e-9 and rho_hat changed by 0.25: both detected, with max \|diff\| reported as 1.0e-9 and 0.25.

## 2. l0star_v2

**Command (job p2va_l0star_v2).** `python -m sim.l0star --set l0star_v2 --seed 20261029 --per-class 500`, run at ed1e716.

**Spec.** README D13 and DESIGN v4 §5 B L0*:
- p = 20, MAF ≥ 0.05, from a 100-kb segment; NFE-mosaic R.
- R̃ = (1 − η)R + ηI with η = 1e-3; n_ref = 1e9.
- True ρ uniform over {0, ±0.3, ±0.5, ±0.8}; rho_hat = ρ, rho_se = 0.
- Nominal N = (1e5, 1e3); trait types gwas/mol.

**Result.** 2,000 loci (S/D/W/G 500 each) from 193 segments and 9,600 candidates.
- Natural class shares, ± MC SE: W .7872 ± .0042, G .0915 ± .0029, D .0623 ± .0025, S .0521 ± .0023, U .0070 ± .0008.
- l0star_v1 for comparison: W .7832, G .0940, D .0662, S .0518, U .0048 (9,650 candidates).
- sha256: h5 `2f9e7558…`, truth `e8b93828…`, stats `6ea8815d…`.

**v2 vs v1: not identical, by construction.** The set name is part of every random key (`rng(seed, set, "segment"|"locus", i)`), so the two sets are different draws from the same spec (`results/p2_verify_artifacts/l0star_v2_vs_v1.json`).

**Reproducibility of v1.** The same job also rebuilt a replica named `l0star_v1` at ed1e716 into `$ORCH_OUT`. The replica is **byte-identical** to the stored `l0star_v1.h5` (sha256 `3b660558…`) and to its truth (`e3d52800…`). In the stats json only `runtime_s` differs (`l0star_v1_replica_vs_stored.json`: identical = true, 2,000/2,000 loci). So the uncommitted code of 17:54 produced the same set as the committed code.
