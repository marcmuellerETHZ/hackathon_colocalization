## 2. What the pipeline does (src/eval/testrun.py, scripts/eval_test.py)
- **One access window.**
  - `eval_test.py` writes `started`, runs every stage, and writes `completed` only after verification passes.
  - Test truth therefore never has to be read after the window closes (review p5_verify_infra defect 2).
  - An error or signal writes `interrupted` and leaves the nonce open. `--resume NONCE` continues the same run (DESIGN §11 M7). `--abandon NONCE` (PI) writes `aborted`.
- **Stages.** Each stage is idempotent.
  - **Real arms.** Test mode: `real_data_arms.builder` = `data.real.extract:build_test_arm` (P3-28). Dry mode: validation subsamples of real_locus_sets@2, or `--dry-real-builder` = the same builder in its validation mode.
  - **Generation** of the main grid and shifted arm. It runs in the main thread, resumes per cell, and does the slowest cells first (PI decision d; L3|P1 first).
  - **Method units.** One harness run per (method × set) with a per-locus checkpoint. CPU units run under the core/RAM budget, largest first; a unit whose full worker count does not fit starts once at least half of its workers are free. GPU units run one at a time after generation. A failed unit is retried once. Slow methods use the nested subsample of `configs/testset_v1.yaml`: ColocBoost 40/40/40, mvSuSiE the first 20 of the same draw (P3-17), shifted cells included.
  - **Evaluation** with `run_benchmark.evaluate_all` and operating points given:
    - C1 joint BCa bootstrap and the C3 test, when there is a candidate;
    - per-method id lists, so a slow method is scored only on its own subsample;
    - C4 slopes;
    - the DESIGN §2.5 real-data criterion, plus the P3-23 ρ sensitivities for the candidate;
    - `claims.json`;
    - `descriptive.json`.
  - **Verification**: `run_benchmark.verify`, which re-runs `verify_run` on every run and recomputes every sub-benchmark; `verify_run` on the real-arm runs; the sha256 of every input.
- **D16 (MVR route).**
  - `candidates.primary: null` is accepted only together with `candidates.decision` (e.g. "D16"). An unfilled template is still refused.
  - `claims.json` then reads C1/C2/C3/C4 = "no candidate (D16)"; C5 is the benchmark.
  - Entries marked `descriptive: true` (famB, famG) are benchmarked, are never the candidate or a C3 baseline, and get three-way calls at both the matched-W operating point and fixed 0.8/0.8 in `descriptive.json`.
- **Harness:**
  - per-locus checkpoint and resume;
  - LPT order (largest p first);
  - a crashed, timed-out or all-failed GPU batch is retried once as single loci (`extra.harness_batch_retry`);
  - `load_ld2` for methods with `needs_ld2` (famA; merged 0663b14);
  - `read_locus_attrs` caches attributes in-process, because the 35k-locus master file took 287 s per read.

## 4. Extrapolation of the full test run (D16 method list)
Command:
```
python scripts/eval_test_extrapolate.py results/eval_test_dry/dry_v4 \
  --methods configs/proposals/test_methods_v1_mvr.yaml --cores 64 --ram-gb 120 --eval-dry-s 371 --dry-cores 8 [--no-pilot-floor]
```
**Assumptions:**
- **Test sizes:**
  - main grid 34 × 340 loci (300 S/D/W plus about 40 G+U) = 11,560;
  - shifted arm 1,600;
  - ColocBoost subsample 38 × 120 = 4,560;
  - mvSuSiE subsample 38 × 60 = 2,280;
  - real arms 800 + 1,237 + 600 × 2 = 3,237 loci, for coloc_abf, both coloc-SuSiE variants, SharePro and strength_only (no candidate, D16).
- **Per-locus cost:** the dry-run mean (central), or the maximum of the dry-run mean and the pilot200 mean (conservative).
- **CPU scheduling:** greedy, largest unit first, on 63 cores and 120 GB, using the tuned worker counts and memory per worker in `configs/proposals/test_methods_v1_mvr.yaml`:

  | method | workers | GB per worker |
  |---|---|---|
  | coloc_susie | 20 | 3.0 |
  | coloc_susie_mm | 20 | 2.8 |
  | mvSuSiE | 14 | 3.0 |
  | ColocBoost | 8 | 1.3 |

  The remaining methods have 2–8 workers. RAM, not cores, limits how many SuSiE-type workers run at once.
- **GPU methods** run serially in parallel with the CPU work.
- **Generation** is scaled from the valid_grid_v1 per-cell timings: about 34 % of valid_grid's candidates, 4 generator workers, LPT order, giving 0.9 h. It comes before the sim units; the real-arm units overlap with it, but this is not credited.
- **Evaluation plus verification**: 371 s in the dry run (566 loci, 8 cores), scaled linearly in loci and by 8/48 bootstrap workers, giving 0.4 h.
- **famG**: GPU serial, not measured in dry_v4 (see §5). GPU work does not lengthen the run unless it exceeds the CPU makespan, about 3–5 h.

| scenario | CPU worker-h | CPU makespan | generation | GPU serial | eval + verify | **total wall** |
|---|---|---|---|---|---|---|
| D16 full list, dry-run rates (central) | 136 | 3.3 h | 0.9 h | 0.1 h (famB) | 0.4 h | **4.6 h** |
| D16 full list, pilot floor (conservative) | 196 | 5.2 h | 0.9 h | 0.1 h | 0.4 h | **6.5 h** |
| drop mvSuSiE (D17 cut 1), conservative | 151 | 3.6 h | 0.9 h | 0.1 h | 0.4 h | 4.9 h |
| also drop ColocBoost ×2 (cut 2), conservative | 142 | 3.6 h | 0.9 h | 0.1 h | 0.4 h | 4.9 h |
| also drop both prop tests (cut 3), conservative | 134 | 3.1 h | 0.9 h | 0.1 h | 0.4 h | 4.4 h |

Method-level worker-hours for the full test (conservative): coloc_susie 62.2, coloc_susie_mm 59.9, mvsusie 44.6, sharepro 10.3, colocboost 8.5, coloc_prop_test 5.4, prop_coloc 3.4. Each of the remaining methods is under 1 h.

**Recommended default:** run the full D16 list.
- Both estimates are at or under 6.5 h.
- The conservative one is driven by the pilot's L4-heavy screen_v2 cells, which are slower than the 34-cell grid.
- If the PI wants margin, the only cut that buys time is D17 cut 1, dropping mvSuSiE: −1.6 h conservative, −1.0 h central. ColocBoost and the prop tests save little.

## 5. Supplementary D16/MVR dry run `p6dr_mvr_v1` (passed after one fix)
Command:
```
python scripts/eval_test.py --dry-run-valid --dry-real-builder --methods configs/proposals/test_methods_dry_v2_mvr.yaml \
  --scale 0.01 --label dry_mvr1 --gen-workers 2 --cores 12 --ram-gb 24
```
- Commit 54f9b92; 12 cores, 24 GB, 8 GB VRAM.
- Sets:
  - main grid 147 loci;
  - shifted arm 16 loci;
  - real arms built by `data.real.extract:build_test_arm` in validation mode: R2 8, R3b 13, R4b 6 × 2.
- **Generation, the real arms and every unit finished.** famB and famG ran through the GPU path, famG with 2 failed / 147.
- **The evaluation then crashed.** The C4 bootstrap got a realistic P2/P3 subset lying in a single LD block, and the BCa jackknife cannot run on one bootstrap unit (`ValueError: need at least one array to concatenate`).
- **Fix.** At the PI's request it is general, not scale-specific: every bootstrap or metric block now records "not estimable" (NaN plus a reason) for an empty or single-unit subset instead of raising. This covers:
  - the run_benchmark bootstrap block and C3;
  - C4;
  - the real-arm criterion (empty arm, or fewer than 2 clusters);
  - the descriptive block.
  Tests: `test_bootstrap_blocks_never_raise_on_empty_or_single_unit_subsets` (empty subset, one block, three blocks), `test_c4_with_a_single_bootstrap_unit_is_not_estimable`, `test_c4_with_no_p2_p3_loci_is_not_estimable`.
- **Resumed with the same label at the final commit c32b511** (job `p6dr_mvr_v1_resume3`: evaluation and verification only, since all units were already done): `DRY RUN OK`, `verify ok: True`. Every harness manifest records commit c32b511 as an orch snapshot.
  - `claims.json`: C1/C2/C3/C4 = "no candidate (D16)", primary null.
  - `descriptive.json`: famB and famG, each with three-way calls at the matched-W and at the fixed 0.8/0.8 points.
  - `real_arms.json`: coloc_abf, coloc_susie, coloc_susie_mm, sharepro and strength_only on the builder-built arms.
- **GPU cost per locus** (harness wall): famB 0.09 s, famG 0.23 s on sim loci. At full size that is about 0.3 h and 0.8 h of serial GPU time. Both run alongside the CPU units (makespan 3.3–5.2 h), so they do not change the §4 totals.

3. **Real subsample seeds:** `freeze_test_ids` used `derive(20261028, "real_test_subsample_v1", arm)`; the PI is amending P3-18 to match.
